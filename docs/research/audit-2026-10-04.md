# Audit 2026-10-04: performance, bundle, accessibility, robustness

Read-only audit of master at `42d4201` (worktree `.claude/worktrees/audit`). No code changed.
Measured with `MIX_ENV=prod` on port 4012 (minified assets, no `data-phx-loc` debug attributes) and Chrome 154 over CDP.
Scripts: Sim fuzz and GameServer load (`mix run`), a WebSocket frame hook in the page, an in-page contrast and target-size scan.

## Summary

- The engine is fast and stable. 2000 random games: 0 exceptions, 0 stalls, 1.2 s wall time.
- The cost is in the LiveView payloads. Each bot or human action sends 38–116 KB of raw JSON to each tab. About 70 % of a 4-seat diff is the hidden player sheets, and about 40 % is inline icon paths.
- The WebSocket process of one tab grew to 9.2 MB of heap (9 KB after a forced GC). On a 256 MB machine, this is the first limit, before CPU or GameServer memory.
- Accessibility: keyboard and dialogs are good (native modal dialogs, visible focus). Main gap: a screen reader gets no announcement when a chip is drawn or a pot explodes.

### Inline SVG per page

`QuacksWeb.Icons` puts each icon's full `<path d>` into the HTML on every use. The 29 icon files are 54 920 B in total.

| Page (host, desktop) | DOM size | `<svg>` count | SVG bytes | Icon bytes |
|---|---|---|---|---|
| Lobby | 10 KB | 1 | 1.7 KB | 1.7 KB |
| Configure | 397 KB | 151 | 243 KB | 235 KB |
| Game, 4 seats, round 1 start | 302 KB | 75 | 231 KB | 118 KB |
| Game, 4 seats, round 1 results | 467 KB | 127 | 412 KB | 215 KB |
| Game, 8 seats, round 1 brewing | 468 KB | 118 | 435 KB | 185 KB |

Biggest repeats: configure book pickers (red ×20 = 55 KB, green ×20 = 50 KB, yellow ×20 = 45 KB, locoweed ×8 = 29 KB). Game page: `vp` (5.8 KB each, ×5–9 = 29–53 KB), `white` (×15–47 = 19–59 KB), `ruby` (×22–24 = 14–15 KB).

**Proposal (sprite):** render one hidden `<svg>` with a `<symbol id="i-{name}">` per icon in the root layout (or serve `/images/icons.svg` with a digest and a long cache). `svg/1` then emits `<svg ...><use href="#i-green"/></svg>`, about 60 B instead of 1–6 KB. The configure DOM drops by about 230 KB. Each game diff drops by 25–40 % (see §2). The `text-*` colour classes keep working because the symbols use `fill="currentColor"`. Run the icon files through svgo with 1-decimal precision too; `victory-point-1.svg` (5.7 KB) is the worst.

## 2. LiveView payloads

Raw frame size, with the size after `deflate-raw` in brackets (what `compress: true` would send):

| Event | 4 seats (1 human, 3 bots) | 8 seats (1 human, 7 bots) |
|---|---|---|
| Lobby join | 8.6 KB (2.8 KB) | – |
| Configure join (host) | 302 KB (24 KB) | – |
| One configure change (add bot) | 6.4–7.1 KB (1.2–1.4 KB) | – |
| Start game | 206–221 KB (29–30 KB) | 306 KB (30 KB) |
| One action (draw, bot tick), early round | 34–41 KB (3.8–6.1 KB) | 60–68 KB (5.8–6.5 KB) |
| One action, pot with 6–8 chips | 60–82 KB (7–9.5 KB) | 105–116 KB (8.4–8.6 KB) |
| Round end (to results) | 181 KB (25 KB) | – |

One human draw makes 1 + (number of bots) diffs within about 0.7 s. At 8 seats one draw cycle is 0.5–0.9 MB raw per tab.

Where the bytes go (one 66 KB diff, 4 seats, mid round):

- 45 KB (68 %): the 4 `sheet-player-N` popovers. Each holds a `player_card` with a small pot and its icons. They are closed almost all the time, but `player_card` takes `game={@game}`, so every action re-renders all 4 cards.
- 14 KB (21 %): the large pot. The 54-space comprehension sends `data-x`/`data-y` and empty slots again on each change.
- 25.7 KB of the 66 KB is icon `<path>` markup (22 paths).

Server render time (telemetry `[:phoenix, :live_view, :render, :stop]`, 33 renders): median 1.1 ms, p90 1.7 ms, max 2.8 ms. `handle_event`: median 0.1 ms.

Ponytail fixes, in order:

1. Sprite icons (§1). No change to the diff structure.
2. Do not render the player sheets on each tick. Either give `player_card` only `player={@game.players[seat]}` and the few derived values (white sum, explode limit, scoring index), so change tracking skips unchanged seats, or render the sheet body only after it opens. A bot that does not change seat N then sends nothing for seat N.
3. In `pot/1`, make the space positions static (one `<g>` per space from a compile-time list, with the per-space dynamic parts only for chips, rings and highlights). `phx-update="ignore"` does not fit here, because the pot must change.
4. Set `websocket: [compress: true]` on the `/live` socket. This makes frames 7–12× smaller. The cost is a zlib context per connection (about 300 KB) and some CPU; take this step after 1 and 2.

Streams and temporary assigns do not help much: the big data is the game struct, which the template reads in many places, and not a growing list. The action log is the one list that grows; it is small in the diff.

## 3. Server

### GameServer memory (sim harness, no HTTP)

100 GameServers with 4 seats each (1 scripted "human" with the AI, 3 bots), `bot_delay: 0`:

- All 100 games finished in 0.56 s wall time, 3.6 s CPU (engine and AI: about 36 ms CPU per 4-seat game).
- GameServer at game end: average 433 KB, max 690 KB. After a forced GC: average 220 KB, max 372 KB.
- BEAM total: 70 MB before, 93 MB after (processes 43 MB).

Log growth (2000-game fuzz, heap size from `:erts_debug.flat_size`):

| Seats | Log entries, average (max) | Game struct heap, average (max) | `external_size` |
|---|---|---|---|
| 1 | 334 (566) | 29 KB (52 KB) | 9 KB |
| 2 | 678 (1234) | 58 KB (108 KB) | 18 KB |
| 4 | 1336 (2263) | 112 KB (184 KB) | 33 KB |
| 8 | 2579 (3882) | 214 KB (338 KB) | 63 KB |

Growth is linear in actions; about 150 log entries per seat over 9 rounds. `Quacks.Session` also keeps the action list for undo. This is not a problem.

Each `{:game, id, game}` broadcast copies the full game into every subscribed LiveView (up to 338 KB heap at 8 seats).

### Idle timeout

`@idle_timeout` is 2 hours, reset by any message (calls, bot ticks). A finished game stays alive for 2 hours (0.2–0.7 MB). Nothing hibernates.

### WebSocket process memory

The `Bandit.DelegatingHandler` process (one per tab, holds the WebSocket) had 9.2 MB of memory after about 40 large diffs. After `:erlang.garbage_collect/1`: 9 KB. The garbage comes from the large JSON frames. The LiveView process itself stayed under 1 MB.

### 100 games × 3 bots on one 256 MB Fly machine

Estimate, with 1 human tab per game:

- GameServers: 100 × 0.2–0.7 MB = 20–70 MB. OK.
- LiveView processes: 100 × under 1 MB. OK.
- WebSocket processes: 100 × up to 9 MB = up to 900 MB before GC. **This can run out of memory.** With `fullsweep_after` set (see recommendations) this goes to a few MB in total.
- CPU: about 3 bot actions per 0.7 s per game, so about 430 renders per second over 100 games × 1.1 ms = about 0.5 of a core for render, plus JSON encoding of 40–80 KB per diff. A shared-cpu-1x machine is near its limit. Bots and the engine are not the problem.
- Outbound traffic: about 250 KB/s raw per tab, 25 MB/s for 100 tabs (about 2.5 MB/s with compression).

Result: with the current payloads, plan for about 30–50 concurrent games on one 256 MB machine. With the sprite, slim player cards, compression and `fullsweep_after`, 100 games is realistic.

## 4. Accessibility

Contrast scan on lobby, configure, board (brewing), round results and shop, at 1280 px and 390 px. Text on parchment, wood and gold buttons passes WCAG AA (ink on parchment 10.1, ink-soft on parchment 6.8, ink on gold 6.7, parchment on wood 6.1, parchment-dim on wood-dark 7.0). Gradients and background images are approximated by their base colour.

Failures and near misses:

| Where | Colours | Ratio | Needs |
|---|---|---|---|
| "Fortune teller" title on the purple card face, 16 px bold | gold on #5f4484 | 4.0 | 4.5 |
| `next_reward` "ruby" in the brewing bar (`game_components.ex:1216`) | ruby on wood-dark | 2.85 | 4.5 |
| House rules line (`game_components.ex:1720`), `text-zinc-500` | zinc-500 on parchment | 3.7 | 4.5 |
| `text-zinc-500` subtitle in `core_components.ex:485` (if on parchment) | same | 3.7 | 4.5 |
| White ingredient icon on orange and green chips (non-text) | white on #e58a2d / #4caf50 | 2.6 / 2.8 | 3.0 |
| Seat colours as text on parchment (if used as text) | gold, lime, sky | 1.4–1.5 | 4.5 |

Chip value badges (ink on parchment-light) and `:xs` chips (ink on orange 5.1, ink on green 4.8, white on blue 4.8) pass.

Focus order in a decision dialog: the dialogs use `showModal()`, so focus stays in the dialog and Esc works. The fortune choice opens with focus on its last option; Tab goes Close → Ingredient books → options. The shop opens on a `focus-start` span, then Close → books → chips → Done → Buy. `:focus-visible` gives a solid outline. In the shop, the 7 book buttons all have the name "Book"; give each its colour ("Pumpkin book").

Icon-only buttons: all have `aria-label` (Close, Menu, Ingredient books, bag, fortune card, colour swatches, steppers). The scan found no unnamed control.

`prefers-reduced-motion`: CSS covers 22 of 25 animated selectors; the view-transition round counter is skipped in JS (`reduced()`), and the pot flight in `app.js` falls back to fades. Not covered: `.fuse[data-exploded]::after` (`fuse-flash`, 650 ms opacity flash).

Touch targets under 44 px (390 px and 1280 px):

- Seat colour swatches 32 × 32 (configure, 8 of them).
- "+ Add bot" 90 × 36, "Copy link" 116 × 38, game link input 38 high, name input 37 high.
- Round results "Skip" 44 × 35; "To the shop" 288 × 42; sheet Close 42 × 42 (CSS says 2.75 rem; the dialog padding shrinks it).
- Header "Quacks" link 75 × 38. Lobby credit links 14 high (inline text links, exempt under WCAG 2.5.8 but small).
- Board at 390 px: no other offenders.

Screen-reader text for the pot: the large pot is `role="group"` "Pot track", and each of its 54 spaces has a `<title>` ("Space 9: 9 coins, 1 VP"). The chips in the pot have `aria-label="white 2"` on a `<g>` (and on a `<span>` for `chip/1`) with no role, so most screen readers ignore it. The small pots have no titles. There is no live region for game events; the only `aria-live` is the flash group.

**A11y blocker (screen reader only):** a draw, an explosion or a bot action is not announced. A blind player must open the log after every draw. Fix: one visually hidden `aria-live="polite"` element with the last log line for this seat ("You drew orange 1. White total 5 of 7.").

No blocker for keyboard or low-vision players.

## 5. Robustness

### GameServer crash mid-game

Test: `Process.exit(pid, :kill)` on a running 4-seat game with an open tab.

- `Quacks.GameServer` is `restart: :temporary` under a `DynamicSupervisor`. The game and its seats are gone. There is no persistence.
- Bots stop. The open page shows the old state and does not notice (no monitor, no message).
- On the next click, `GameServer.apply/3` returns `{:error, :not_found}`. The `with` in `handle_event("action", ...)` has no clause for it, so the LiveView raises `WithClauseError`, crashes and rejoins. `mount/3` gets `:not_found` and goes to the lobby with the flash "Game yyxqts does not exist."
- Result: the user recovers, but through a crash, and only after an action. Other events that call the server (`handle_info({:names, ...})` matches `{:ok, table}`) crash the same way.

### Fuzz

2000 games with `Quacks.AI.Sim.play/3`: 1–8 seats, random profiles (balanced, cautious, reckless), every expansion combination, every house rule value, random Ingredient Sets (black 1–3, orange 1–2, locoweed nil/1–6, 3 with The Alchemists). Result: 2000 finished, 0 exceptions, 0 stalls (`Quacks.AI.Stall`), 0 timeouts. Wall time 1.15 s on 10+ cores; slowest game 28 ms.

### Static analysis

- `mix credo --strict`: no issues (1796 mods/funs, 92 files).
- Dialyzer: `dialyxir` is a dependency, but there is no PLT (none in `_build`, `priv/plts` or `~/.mix`). I did not run it. The first PLT build (ERTS, Elixir, Phoenix, LiveView, Bandit) costs about 5–10 minutes and 0.5–1 GB of disk; later runs take under a minute. Set `plt_local_path: "priv/plts"` and git-ignore it, so the PLT survives `_build` cleans.
