React ships the app to the browser and diffs there. LiveView keeps the app on the server and ships the diff. This lesson opens the diff and looks at its bytes.

Two renders, one process

A tab’s life starts with a plain HTTP request. mount/3 runs, render/1 runs, and the full HTML goes back for a fast first paint. No process is kept. Then app.js opens the websocket and LiveView starts a new process that mounts again. connected?/1 tells the two apart, which is why only the second subscribes and is watched by the GameServer.

From then on the process loops like any GenServer: handle_event/3 for browser events, handle_info/2 for mailbox messages, and after each one LiveView calls render/1 and diffs. The game page picks its template with function heads you already know how to read:

No game yet: the configure screen. Otherwise: the board. The begin broadcast sets @game, and the next render matches the second clause.

React ≈Server rendering plus hydration, except nothing hydrates. The second mount builds fresh server state, and the browser only ever receives HTML and patches.

Statics once, dynamics on change

HEEx compiles a template into statics, the literal HTML between expressions, and dynamics, the {...} slots. The connected mount sends both. After that, LiveView re-runs only the slots whose assigns changed and sends only those (Assigns and HEEx: change tracking).

Where tracking helps, and where it doesn’t

Helps: sheets that render only when open. Each player sheet’s body is behind :if={@open_sheet == seat}. A closed sheet renders nothing, so a move sends nothing for it.

Hurts: the whole @game as one assign. LiveView can track @game.round on its own, but an expression like results?(@game) or a component given game={@game} depends on the whole struct. The struct changes on every move by anyone, because the log grows. So every such slot re-runs on every move, in every tab. game_live.ex passes game={@game} to about twenty components.

Hurts: a list that grows at the front. The log sheet sits behind the menu, but it is always rendered. Its rows come from a comprehension, and LiveView tracks comprehension rows by index. A new line goes in at index 0, so every row moves one index down and all of them count as changed.

Add it up and the repo’s own glossary says it plainly: “Every game diff is tens of KB of JSON” (CONTEXT.md, live socket). That is why the endpoint sets fullsweep_after: 0: the garbage from big diffs piled up in each socket process.

React ≈Passing the whole store to every component instead of a selector. In React it costs renders; here it costs renders and bytes on the wire, per tab.

Streams and temporary assigns

  • Streams (stream/4, stream_insert/4) send each item once with a DOM id, then forget it on the server. Inserting at the top sends one row. Good for long feeds; the server cannot re-read the list later.
  • Temporary assigns reset an assign to a default after each render, so the server does not keep it. The older tool for the same job; streams cover most uses now.
  • :key on a comprehension tracks rows by an id instead of the index, so a prepend sends only the new row while the server keeps the list.

Quacks uses none of them yet. For the log, a stream or a :key (each log entry’s position from the end is a stable id) would cut the bytes. A stream would not save memory here, since the full log already sits inside @game.

One more cost to keep in mind: each tab’s LiveView holds its own @game. A PubSub broadcast copies the struct into every subscriber’s heap. Four tabs, four copies. Lesson 7 measures it.
