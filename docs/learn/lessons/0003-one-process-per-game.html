In React, state lives inside a component and dies with it. In Quacks, the game’s state lives inside a process that no tab owns. Tabs come and go; the process keeps the game and takes one message at a time.

A process in eight lines

Strip away OTP and a process is three primitives: spawn starts a function in a new process, send drops a message in a mailbox, receive takes one out by pattern. This sketch is not in the repo; it is what the GameServer is built from.

receive picks the first message that matches a clause, the same way a function picks its first matching head. Messages are copied into the receiver’s memory. Nothing is shared (Elixir guide: Processes).

React ≈A Web Worker with postMessage and onmessage, except a BEAM process costs a few KB, so you start one per game without a second thought.

GenServer: that loop, packaged

Writing receive loops by hand gets old. A GenServer is OTP’s ready-made loop: wait for a message, call your callback, keep the state it returns, wait again. You write only the callbacks, and each one is a function with pattern-matched heads. Three kinds of message, three callbacks:

Sent withLands inCaller waits?In Quacks
GenServer.call/3handle_call/3yes, for the replyevery move, seat claim, get
GenServer.cast/2handle_cast/2nonot used at all
send/2, timers, monitorshandle_info/2nobot ticks, file writes, :DOWN, idle timeout

The GameServer routes every call through one head and fans out to private server_call/3 clauses. Read them like lesson 2’s die_rolls: first match wins.

The return value is an instruction to the loop. {:reply, reply, new_state, timeout} means: send reply to the caller, keep new_state, and if no message comes within timeout, send me :timeout. That fourth element is the two-hour idle timer, nothing to do with the caller.

Messages nobody waits for go to handle_info/2. Note the guard on the bot tick: a tick that is not the seat’s pending number falls through to the next clause and is dropped.

React ≈useReducer, where the reducer is split into clauses and the dispatcher is a queue. The difference is lifetime: this reducer’s state outlives every component that reads it.

How a game id finds its process

Two children of the application make this work (application.ex:16–18): a Registry that maps names to pids, and a DynamicSupervisor that starts with no children and gains one per game.

A new game asks the DynamicSupervisor for a child. If two games draw the same six letters, the Registry refuses the second name and the code just picks another id.

The supervisor calls start_link/1, which registers the new process under its id with a :via name:

From then on, every client function does what you saw in lesson 1’s hop 4: Registry.lookup(Quacks.GameRegistry, id), then GenServer.call(pid, msg) (game_server.ex:554–562). No list of games is kept anywhere else.

The state is a plain map

init/1 builds the state once. It holds the session (the game plus its moves, nil while the table waits) and the table around it: tokens, names, bots, pages, timers.

    Timeouts: the two kinds
    

      
  
    • The call timeout is the caller’s. GenServer.call/2 waits 5 seconds by default, then the caller exits with :timeout. Quacks never sets another value (docs).
      • 
  
    • The idle timeout is the server’s. The @idle_timeout in every return tuple is 2 hours; when it fires, server_info(:timeout, state) deletes the game file and returns {:stop, :normal, state} (game_server.ex:963).
      • 

    

    One consequence for review: anything slow inside a callback delays every message behind it. Bot planning runs inside the GameServer (plan/2, up to 30 AI.decide calls, game_server.ex:1118). If a callback ever took more than 5 seconds, the waiting tab’s call would exit with :timeout, and call/2 only catches :noproc, :normal, :shutdown and :killed. That tab’s LiveView would crash and remount. Worth keeping in mind when a PR makes the bots think harder.
    

    React ≈Like a long synchronous task on the main thread: everything queued behind it waits. Here the “thread” is one game, so other games keep running.
