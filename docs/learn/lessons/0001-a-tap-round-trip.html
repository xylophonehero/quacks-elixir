A tap’s round trip

Yields
You can name the nine hops a tap on Draw a chip takes, and say which process runs each one.
You bring
React state, a websocket, and the idea of a reducer.
Guide
Ch. 4, GameServer and Ch. 5, LiveView

In a React app the browser holds the state and the server is a database behind an API. Quacks flips that. The state lives on the server, in a process, and the browser is a thin screen that sends taps and receives patches.

React ≈Think of the GameServer as a Redux store that lives on the server, one per game. Every tab subscribes to it. Nobody keeps a copy they can edit.

Two kinds of process do the work. A process on the BEAM (the Erlang virtual machine) is a tiny isolated worker with its own memory and a mailbox. It shares nothing and talks only by sending messages. A server can run hundreds of thousands of them (Elixir guide: Processes).

  • GameLive, one per open tab. It holds that tab’s view state in its assigns and renders HTML.
  • GameServer, one per game. It holds the game and applies every move.

Between them sits PubSub, a message bus inside the same node. The engine, Quacks.Game, is no process at all. It is plain functions that the GameServer calls.

Step through one tap

Tab A is seat 0 and taps Draw a chip. Tab B is seat 1 and watches. Tap Next to follow the move. The diagram lights the parts each hop touches.

  1. 1 The tap

    The button is plain HEEx, Phoenix’s HTML template language. phx-click names the event. phx-value-action attaches the move, an Elixir term turned into a URL-safe string by encode/1. The button is disabled unless :draw is in @actions, the list the engine says is legal.

    React ≈<button onClick={() => dispatch(draw)} disabled={!actions.includes("draw")}>. The difference: there is no handler in the browser. The click is data that travels to the server.

  2. 2 Over the websocket

    When the page loaded, app.js opened one websocket to /live. LiveView’s client sends the event over it: the name "action" and the params %{"action" => "g2gC..."}. No new HTTP request is made.

    React ≈A socket.send(JSON.stringify({event, params})) on a socket that stays open. LiveView writes this client for you (Bindings guide).

  3. 3 handle_event in tab A’s process

    On the server, the event lands in the mailbox of tab A’s GameLive process. Elixir picks the first handle_event clause whose pattern fits. This one needs an integer seat in the assigns, so a spectator (seat nil) falls to the second clause. It decodes the move and calls play/3.

    React ≈A component instance that lives on the server. socket.assigns is its state. The seat comes from there, so the browser cannot claim another seat.

  4. 4 GenServer.call to the game

    play/3 calls GameServer.apply/3. That function runs in tab A’s process. It finds the game’s pid by id in the Registry and sends {:apply, 0, :draw} with GenServer.call. Tab A’s process now waits for the reply.

    The message joins the GameServer’s mailbox. The GameServer takes one message at a time. That single fact is why two taps can never race.

    React ≈await store.dispatch(action), where the store is a separate worker with a queue in front of it.

  5. 5 The engine decides

    Every call goes through one handle_call/3 that hands the message to a private server_call/3. The :apply clause asks the session to apply the move. The session calls the pure engine.

    Game.apply/3 takes a game and returns a new one. It never touches a process, a socket or a clock. Lesson 2 reads it line by line.

    React ≈The reducer: (state, action) => state. It also returns an error tuple for an illegal move instead of throwing.

  6. 6 Broadcast to the topic

    reply_game/1 does two things. First it broadcasts {:game, id, game} on the topic "game:abcdef". Then it returns the reply for the caller.

    The broadcast sends the whole struct to each subscriber, in memory. Nothing crosses the network yet.

    React ≈store.subscribe(listener) firing for every listener. Here each listener is another process with its own mailbox.

  7. 7 The reply reaches tab A

    GenServer.call returns {:ok, game} inside play/3. put_game/2 stores the game and works out the derived assigns once: @me, @decision and @actions.

    React ≈setState plus selectors. put_game/2 is the only place that sets these assigns, so the reply path and the broadcast path cannot disagree.

  8. 8 handle_info in every tab

    Each GameLive subscribed in mount/3, but only on the connected mount, the one that runs in a process for the life of the tab (game_live.ex:126). The broadcast arrives as a plain message. Tab B takes the new game. Tab A already has it from the reply, so it skips the copy. It also skips an older copy that arrives late, using the log length as a version number.

    React ≈A subscription callback. game == current compares deeply by value, with no custom equals.

  9. 9 Re-render and send the diff

    After each callback returns, LiveView re-renders the template. It tracks which assigns changed and which parts of the template read them, then sends only the changed dynamic parts as JSON over each tab’s websocket. The client patches the DOM. Tab A sees its chip land. Tab B sees the same chip land in seat 0’s pot.

    The static HTML went down once, on the first load. From then on only the changed values travel (Assigns and HEEx templates).

    React ≈Reconciliation, run on the server. React diffs a virtual DOM in the browser. LiveView diffs on the server and ships the patch.

Two tabs, one moment

What if tab A and tab B both tap at the same instant? Each tab’s process sends a {:apply, ...} message. Both land in the one GameServer mailbox, in some order. The GameServer applies the first, replies and broadcasts. Then it takes the second message and applies it to the new game. If the second move is no longer legal, the engine returns an error and that tab shows a flash. No locks, no transactions. The module doc says it plainly:

It serialises the moves (two clicks at the same moment are applied one after the other, never on top of each other). lib/quacks/game_server.ex:5–13
React ≈Like a reducer called by one dispatcher in a strict queue. In the browser, JavaScript’s single thread gives you this for free. On a server with many cores, the mailbox gives it to you per game.

One more reason the GameServer uses call and never cast: call waits for an answer. A tab always learns whether its move worked, and a fast clicker cannot flood the queue.
