Elixir code rarely wraps work in try. A process that hits something unexpected dies, and a supervisor decides what to start again. The design question moves from “how do I catch this?” to “what should a crash take down with it?”

The tree

When the app boots, Quacks.Application.start/2 starts one supervisor with seven children, in order.

Two settings decide what happens after a crash (Supervisor docs):

SettingValuesIn Quacks
Strategy (the supervisor’s):one_for_one restart only the crashed child; :one_for_all restart all; :rest_for_one restart it and those started after itboth supervisors use :one_for_one
Restart (the child’s):permanent always; :transient only after an abnormal exit; :temporary neverGameServer is :temporary; the rest are :permanent

One guard rail: a supervisor allows 3 restarts in 5 seconds by default. One more and it gives up and exits itself, so its own supervisor deals with it. At the top, that stops the application and the VM.

React ≈An error boundary that unmounts the broken subtree and mounts it fresh. The supervisor is the boundary; the restart strategy says how much of the subtree to remount.

    Links and monitors

    Two ways for one process to hear about another’s death:

    • A link is two-way. When one side exits abnormally, the exit signal kills the other too, unless it traps exits; then the signal arrives as an {:EXIT, pid, reason} message. Supervisors link to their children. A Registry links to every process registered in it.
    • A monitor is one-way and never kills. The watcher gets {:DOWN, ref, :process, pid, reason} in its mailbox.

    The GameServer monitors each page that claims a seat. A tab that closes must not take the game down; it only makes a seat absent.

    And the GameServer traps exits, so that a shutdown from its supervisor runs terminate/2 and writes any pending game file:

    terminate/2 also runs when a callback raises, so a crash writes its last pending change too (terminate/2 docs).

    React ≈A monitor is addEventListener("close") on someone else’s socket. A link is two components that share one error boundary.

    What a game keeps

    Its state is in the process, so a crash loses the process’s memory. What is left is the game file: each change schedules a write of the seed, the moves and the table, at most once per 500 ms. A crash leaves the file on disk. Only the idle timeout and a finished game’s expiry delete it.

    But nothing reads the file until the next boot. Quacks.GameStore restores every game file once, as a child of the application, and then returns :ignore: there is no process to call later (game_store.ex:118–130). So a crashed game is gone until the next deploy or restart, then it comes back.

    Meanwhile, its tabs learn on their next call. call/2 turns a missing process into {:error, :not_found}, and every handler ends the same way:

    Read the catch guard closely. If the GameServer raises while handling your call, your call exits with the exception as its reason, not one of those four atoms. The guard fails, the exit is not caught, and your LiveView crashes too. The browser remounts it, mount/3 finds no game and says “Game abcdef does not exist.” Same end, different words. The guide’s chapter 4 says this case is caught; it is only caught for those four reasons.

    Rejoining is not a crash path. A crashed LiveView remounts with the same player_token cookie and gets its seat back from claim_seat. rejoin/4 is for a browser that lost the cookie.

    A review question

    Why :temporary and not :transient with a reload from the game file? A bug that crashes a game on a certain move would crash it again on reload, three times in five seconds, and then the DynamicSupervisor itself would give up, taking every other game with it. :temporary keeps one bad game from ending all of them. The cost is that a crashed game waits for the next boot.
